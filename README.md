# 阅读社统导工作台

这是一个按期次连接飞书 Base、并使用 Cloudflare D1 持久化分组历史的阅读社管理平台。飞书保存社员、荐书、选书以及写回的状态和组号；D1 保存每次确认后的有效选书快照、完整分组和历史搭档关系。平台负责同步两边数据、展示与导出本期书单、检查选书并生成讨论分组。

生产地址：<https://reading-club-coordinator.hanya.workers.dev>

书导和统导的日常操作见：[书导与统导使用说明](docs/书导与统导使用说明.md)。

## 当前功能

- 按 `YYYY-MM` 期次读取独立的推书表和选书表。
- 只展示“推书汇总”中已勾选 `入选` 的书目。
- 导出包含期号、书名、推荐信息和推荐人的 PNG 书单卡片。
- 检查漏选、陌生姓名、重复选书和重复提交。
- 按每本书分别分组，默认两人一组，奇数时最后一组三人。
- 使用历史分组执行贪心匹配，优先安排以前没有一起讨论过的人。
- 将有效状态和各本书组号写回本期飞书选书表。
- 在 Cloudflare D1 保存全部已确认历史，平台展示最近 12 期汇总和完整分组明细。
- 单管理员账号登录；已移除校验码功能。

## 飞书数据约定

平台不会创建、删除或修改飞书数据表、字段和表单。每期由书导在同一个 Base 中人工创建或复制以下两张表。

### 推书汇总

- 数据表名：`推书汇总｜YYYY-MM`
- 表单名：`YYYY-MM 荐书表单`
- 必须字段：`书名`、`推书人`、`推荐语`、`入选`
- 可选字段：`顺序`、`提交时间`

作者、译者等信息直接写入 `推荐语`，不设置单独的作者字段。平台只读取已勾选 `入选` 且书名不为空的记录；有 `顺序` 时按正整数升序展示，没有时按飞书记录顺序展示。

### 选书汇总

- 数据表名：`选书汇总｜YYYY-MM`
- 表单名：`YYYY-MM 选书表单`
- 必须字段：`姓名/昵称`、`选书1`、`选书2`、`选书3`、`有效状态`、`选书1组号`、`选书2组号`、`选书3组号`
- 建议字段：`提交时间`

表单只需要向社员展示姓名和 `选书1—3`；有效状态及组号字段由平台写回。每人选择 1—3 本，三个选书字段不能重复。

### 社员名单

社员名单表由环境变量 `LARK_MEMBER_TABLE_ID` 指定，至少需要：

- `姓名/昵称`
- `是否在籍`

只有勾选 `是否在籍`、且姓名唯一的社员会进入漏选统计和有效匹配。

## 平台操作链路

1. 书导在飞书人工建立本期两张汇总表及对应表单。
2. 荐书结束后，书导在推书汇总中勾选最终入选书目，并更新选书表单的 6 本候选书。
3. 平台输入同一期号，点击“同步”，校验表名和必需字段并显示本期书单。
4. 选书结束后，统导点击“预览结果”，先检查漏选、无效记录和分组。
5. 确认无误后点击“确认并写回飞书”。平台更新有效状态与组号，并覆盖保存该期 D1 历史。
6. 后续期次分组自动读取历史搭档关系；平台“数据库历史”区域可展开查看明细。

## 匹配算法原理

匹配以“每本书”为单位独立执行。同一位社员选择多本书时，会分别进入对应书目的分组。

### 1. 先确定有效选书记录

1. 姓名经过全角/半角、大小写和首尾空格归一化后，与在籍社员名单匹配。
2. 缺少姓名、姓名不在名单、名单中有重名、没有选书或重复选择同一本书的记录标记为无效。
3. 同一人提交多次时，仅保留最新一条有效提交；更早的记录标记为 `已替代`。
4. 在籍但没有有效提交的人进入漏选名单。

### 2. 决定小组人数

- 2 人：`2`
- 4 人：`2 + 2`
- 5 人：`2 + 3`
- 7 人：`2 + 2 + 3`
- 其他人数同理：尽量全部两人一组，奇数时把最后 3 人放在同一组。
- 某本书只有 1 人时标记为 `待协调`。

### 3. 从历史生成搭档成本

平台读取除当前期次外的历史分组。三人组会拆成三对搭档关系，并为每一对统计：

- 过去共同分组的总次数；
- 是否在最近一期共同分组。

### 4. 贪心选择成员

每创建一组时：

1. 先选择“可用新搭档最少”的成员作为锚点，让最难安排的人优先分组。
2. 再从剩余成员中选择成本最低的人，比较顺序为：
   - 优先从未和组内任何人同组；
   - 其次避免最近一期同组；
   - 再尽量减少历史累计同组次数。
3. 三人组在选择第二、第三人时，会计算候选人与当前组内所有成员的合计成本。
4. 成本完全相同时，使用“期次 + 书名 + 成员”的稳定哈希排序，因此同一批数据重复预览会得到一致结果。

这是贪心算法，不承诺全局数学最优，但能稳定地优先避开历史搭档，同时满足两人组和末组三人的人数规则。

### 5. 写回与历史更新

平台根据社员选择书目的原始位置，将组号分别写入 `选书1组号`、`选书2组号`、`选书3组号`。确认写回时会先清空该记录旧组号，再写入本次结果；同一期再次确认会覆盖该期 D1 历史，不会重复累计。

## 数据库设计

系统有数据库，使用 Cloudflare D1，数据库名为 `reading-club-coordinator-db`。飞书和 D1 的分工如下：

- 飞书 Base 是业务数据源：保存社员名单、荐书提交、入选书目、社员选书、有效状态和写回组号。
- Cloudflare D1 是平台历史数据库：保存已确认期次的汇总、有效选书快照、小组和小组成员，用于展示历史及计算下一期的历史搭档成本。
- 点击“预览结果”只计算、不写数据库；点击“确认并写回飞书”后，才会同时更新飞书并保存 D1。

D1 使用四张表：

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `rounds` | 每期汇总 | 期号、在籍数、有效提交数、漏选数、分组数、写回时间 |
| `selections` | 每期每人的有效选书 | 期号、成员标识、姓名、飞书记录 ID、选书 JSON、提交时间 |
| `groups` | 每期每本书的小组 | 小组 ID、期号、书名、组号、状态、创建时间 |
| `group_members` | 小组成员明细 | 小组 ID、成员标识、姓名 |

`selections` 以“期号 + 成员”为主键，`group_members` 以“小组 + 成员”为主键。同一期重新写回时，先删除该期旧选书和旧分组，再在一个 D1 批次中保存新结果。

## 接口

所有业务接口均要求管理员会话：

- `GET /api/round-tables?round=YYYY-MM`：发现本期期次表和表单。
- `POST /api/round-tables`：校验本期两张表及必需字段，不创建表结构。
- `GET /api/round-books?round=YYYY-MM`：读取本期已勾选入选的书目。
- `POST /api/grouping`：预览分组；传入 `apply: true` 时写回飞书并保存历史。
- `GET /api/history`：读取最近 12 期历史及分组明细。
- `GET /api/health`：检查飞书和 D1 配置。

## 本地开发

要求 Node.js `>= 22.13.0`。

```bash
npm install
cp .env.example .dev.vars
npm run dev
```

需要配置：

- `LARK_APP_ID`
- `LARK_APP_SECRET`
- `LARK_BASE_TOKEN`
- `LARK_MEMBER_TABLE_ID`
- `ADMIN_PASSWORD`
- `ADMIN_SESSION_SECRET`

常用命令：

```bash
npm run lint
npm test
npm run db:migrate:remote
npm run deploy
```

部署目标为 Cloudflare Workers，历史数据库为 `reading-club-coordinator-db`。
